# 切换服务时保持当前项目上下文（需求记录）

- 日期：2026-11-20
- 状态：草稿（待产品/前端评审排期）
- 类型：产品体验需求（导航交互）
- 提出背景：本地使用/验证时发现，用户在已选定项目下从一个服务切换到另一个服务后，常需重新选择项目，操作割裂。

## 1. 背景与现状

BK-CI 控制台为多服务入口（流水线、代码库、制品库等），多数业务能力以“项目（`projectId`/`projectCode`）”为维度。当前顶部导航中，项目选择与服务切换是两个相对独立的动作。

**现状表现**：用户已在项目 A 下工作，点击顶部“服务”菜单切换到服务 B 时，目标页面往往未自动落在项目 A 的上下文中，用户需要再次在项目选择器中选择项目 A（或等效操作）才能继续项目内操作。

## 2. 问题与影响

- **体验割裂**：跨服务协作（如从流水线查看关联代码库/凭据/制品等）时重复选项目，增加操作成本。
- **易误操作/困惑**：用户可能误以为项目已保留，或在无项目/默认项目上下文下执行操作；也可能误判为“不会用”。
- **结论（基于当前前端实现）**：更接近**通用产品能力缺失**，而非单纯用户操作问题。

## 3. 现状成因（代码线索，`devops-nav`）

> 以下为记录需求时的实现观察，供方案设计参考，不代表最终改法。

- **服务跳转未携带当前项目**：服务菜单/收藏项点击通过服务元数据 `link_new` 拼为 `/console/<link_new>` 后直接跳转，未读取并附加当前路由中的 `projectId`。
  - `src/frontend/devops-nav/src/components/Header/NavMenu.vue`（`gotoPage` / `addConsole(service.link_new)`）
  - `src/frontend/devops-nav/src/components/NavBox/index.vue`（`gotoPage` / `addConsole(child.link_new)`）
- **仅特定场景做项目注入/保留**：同服务 iframe 内部“返回首页”会触发 `goHome` 事件；跨服务切换未复用“按项目进入服务”的路径构造。
  - Header 存在按 `currentPage.project_id_type`/`link_new` 拼接项目路径或 `?projectId=` 的 `goHomeById`（`src/frontend/devops-nav/src/components/Header/index.vue`），但跨服务菜单跳转未统一复用该逻辑。
- **项目标识的存储与补全有限**：切换项目时会更新路由参数并写 `X-DEVOPS-PROJECT-ID` cookie；路由守卫可基于 params/cookie 做一定补全（`src/frontend/devops-nav/src/router/index.ts`：`getProjectId`/`initProjectId`/`goNext`；`src/frontend/devops-nav/src/index.html`：`setProjectIdCookie` 等）。但若服务入口 `link_new` 对应路由本身非项目维度，或未约定项目参数位置，仍无法保证落到“服务 B 的项目 A 页面”。

## 4. 需求目标

1. **默认保持项目上下文**：用户在已选择项目 P 的前提下切换到另一服务 S 时，系统应尽可能保持项目 P，并进入 S 中与 P 对应的默认/入口页面（如该服务支持项目维度）。
2. **行为一致可预期**：顶部项目选择器展示、实际数据/权限上下文与 URL/路由状态一致，避免“显示为 P、实际未带 P”或反之。
3. **合理兜底**：对无权限项目、项目不存在/未启用、或目标服务不支持项目维度等情况，提供明确且一致的降级行为（如回到服务入口并提示选择项目/无权限），不产生静默错误。

## 5. 期望行为与验收要点（建议）

- [ ] AC1：在项目 P 下，从服务 A 通过顶部服务导航切换到支持项目维度的服务 B，默认进入服务 B 且上下文为项目 P（无需再次手选）。
- [ ] AC2：切换后刷新页面/再次在 B 内导航，项目上下文保持为 P（与现有 cookie/路由策略一致且不回退）。
- [ ] AC3：用户对项目 P 在服务 B 无访问权限时，给出与现有权限体系一致的提示/引导（如申请权限或切换项目），不展示 P 的业务数据。
- [ ] AC4：当前未选择任何有效项目时，切换服务行为与现有逻辑一致（引导选择项目或进入非项目页），不引入回归。
- [ ] AC5：对 `project_id_type` 为 path/query 等不同服务元数据形态，跳转均能正确携带项目标识（需梳理 `serviceObject`/`link_new`/`show_project_list` 等配置约定）。
- [ ] AC6：从收藏服务、服务面板等不同入口切换服务，行为一致。

## 6. 范围与非目标

- **范围（建议）**：控制台导航层（`devops-nav`）的跨服务跳转与项目上下文传递；必要时补充服务入口路由对项目参数/cookie 的落地约定。
- **非目标（本需求不直接覆盖，除非评审纳入）**：
  - 重构各业务微前端/子服务内部的全部路由结构；
  - 记忆“每个服务分别的最近项目”（可作为后续增强单独评估）；
  - 权限模型与项目模型本身的变更。

## 7. 待澄清问题（评审）

- 目标服务的“项目默认首页”规则：统一约定还是按服务元数据配置？
- 当目标服务不支持项目维度（或入口为全局页）时，是否仍保留顶部选中项目但不强行注入参数？
- 跨租户/灰度项目（若存在 `gray` 等差异）切换服务时是否需要与现有 `goHomeById` 的 reload 策略对齐？
- 是否需要埋点/观测“切换服务后发生项目重选”的频率以验证收益？

## 8. 关联与参考

- 用户反馈原始问题：“为什么每次切换服务，要重新选项目？”（结论：产品交互/路由衔接能力待补齐，非用户操作错误）。
